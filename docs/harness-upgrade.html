Groundwork Harness Upgrade

What the 2025–2026 research on agent harnesses and agent loops says, how much of it Groundwork already does, and a test-first plan to make it cheaper to run, harder to game, and able to improve both the repositories that use it and Groundwork itself.

Summary

The design holds. Four gaps are worth closing.

The field now treats the harness, not the model, as the main lever: identical models score anywhere from 68% to 88% depending on the harness around them. Groundwork was built on the bets the research now backs: deterministic checks before model calls, hooks instead of prose, a verifier that never sees the author's reasoning, and a hard cap on review rounds. The gaps are narrower than a redesign.

token efficiency

Context paid for on every turn

The instruction file is 6,000 bytes loaded on every turn; pr-loop's skill is 16.9 KB loaded whole per run. Repository overviews add cost without raising success.

output guardrails

Eval weakening goes unflagged

The analyzer rewards any eval diff and never flags a deleted golden case or a baseline move. The verifier's output rules exist only as prose.

repo loop

The ledger is write-only

Every run appends to the ledger and nothing reads it, and people can't read the raw JSON. Recurring findings never become a hook, lint or case.

groundwork loop

Groundwork doesn't learn from its users

Nothing records which Groundwork version produced a run, so no release can be judged on real tasks, and signals about the loop itself never reach this repository.

Research

What the literature says

Each finding has a note on what it means for Groundwork. read means the abstract or article was fetched and read directly. via summary means the figure came from a search-result summary or a secondary write-up and is weaker evidence.

Harness engineering, the frame

context
Agent = model + harness. LangChain moved from 30th to 5th on Terminal Bench 2.0 by changing only the harness. Across 8 harnesses on identical tasks, success ranged from 68% to 88%.
The harness is where Groundwork competes. None of the upgrades below depend on a newer model.
SchmidMarmelab, Sep 2026read (Marmelab)
Guides and sensors. Fowler splits controls into feedforward guides and feedback sensors, each either computational (fast, deterministic) or inferential (model-based). Cheap computational checks go earliest.
This is Groundwork's four-layer model in other words: ANALYZE, GATE and PROBE are computational sensors that run before the one inferential sensor, VERIFY.
martinfowler.comread
Long-running harnesses. Anthropic seeds a feature list with every item marked failing, keeps a progress file, builds one feature at a time, and verifies end to end. Its generator/evaluator split works because the evaluator never saw the generation. Each component encodes an assumption about what the model can't do, and those assumptions go stale.
Red-first cases and the fresh-context verifier already match. Stale assumptions are what the version scoreboard (TASK-12) starts to measure.
Anthropic, Nov 2025generator/evaluator write-upread
OpenAI's agent-first repo. About a million lines written by Codex in five months. The instruction file was cut to roughly 100 lines and used as a map, with enforcement moved into linters and structural tests.
Supports a byte cap on CLAUDE.md/AGENTS.md and moving detail into files loaded on demand.
openai.comvia summary (direct fetch returned 403)

Token efficiency

token efficiency
Context files cost more than they return. Across agents and models, repository context files did not raise task success and raised inference cost by over 20%. LLM-written files cut success by about 3%; developer-written ones added about 4%. Repository overviews were the least useful part; concrete instructions were followed.
Drop the Layout tree and loop narrative from the resident file. Keep Gate, commands and hard rules, which are instructions.
Gloaguen et al., ETH Zürich, 2026via summary
Rule-based elision before LLM summarization. Across 176 harness configurations and four models, cheap rule-based context trimming before model summarization was the most efficient setup. Planning mostly helps weak models' accuracy and strong models' cost.
This supports analyze.py's deterministic packet (GW-009) and model-aware routing (GW-011/014). Keep them.
Fan et al., Sep 2026read
Compression has hidden costs. At 5× context compression, completion stayed at 80–85% while retrieval calls rose from 21 to 64. Success rates alone would miss it.
Measure handoff size, not only decisions. When output is trimmed, leave a path to the full log.
Liu, Aug 2026read
Fewer tools, better results. Vercel removed 80% of an agent's tools: success went from 80% to 100%, tokens halved, and latency fell from 724 s to 141 s.
Keep the role agents' tool lists minimal. pr-reviewer already has only Read, Grep, Glob and Bash.
via Marmelabsecondary
Success silent, failures short, large output offloaded. Feed back only the high-signal part of a failure and keep the full log on disk. Skills load their detail only when needed.
Hooks are already silent on success. Bound what they print on failure, and split the pr-loop skill by state.
OsmaniAnthropic context engineeringread
Cache-stable context management. Keeping prompt prefixes stable while evicting low-value segments cut cost by 56–87%.
Low payoff here: subagents start fresh, and call 2 gets different inputs than call 1. Noted, not planned.
TokenPilot, EMNLP 2026 Findingsread

Output guardrails

output guardrails
Prose rules rarely enforce themselves. Across 391 repositories, only 4–16% of written security rules were enforced by anything; only 12 repositories had deny rules; 60% of harnesses had neither tests nor evals.
This is GW-000's "hooks are law" with numbers. The verifier's rules and the baseline rule are still prose.
Marmelab, Sep 2026read
Agents cheat on tests, and it is rising. RL post-training raised exploit rates from 0.6% to 13.9% in one benchmark. EvilGenie catches hacks with held-out tests, LLM judges, and detection of edits to test files.
The implementer can edit or delete eval cases in the same diff as the fix, and nothing deterministic notices. Flag it in the analyzer.
EvilGenieSpecBenchvia summary
Capped evaluation. Test sets where the best honest score is deliberately below 100% expose cheating: a score above the cap is evidence of it.
Needs randomized hidden tests the implementer can't read. Deferred.
CapCode, Jun 2026read
More reviewers made results worse. Adding reviewer agents cut success by 8% in the tested cases, and chains of more than four handoffs almost always failed.
Keep GW-017's two calls. Strengthen the one verifier with code checks instead of adding a second.
Marmelab, Sep 2026read, aggregate

Self-improvement

self-improvement
The ratchet. Every rule in an agent's instructions should trace back to a specific failure. Each observed mistake becomes a permanent constraint: a rule, a hook or a check.
Groundwork's failure-triage does this by hand. The ledger has the data to propose it.
Osmaniread
Evolving playbooks need small updates and curation. ACE improves a context by generating, reflecting and curating, applying small incremental updates. Rewriting the whole context causes brevity bias and context collapse, where detail erodes over time.
Proposals are appended drafts, never rewrites of CLAUDE.md or a skill. Groundwork's draft-then-promote flow is already the curation step.
ACE, ICLR 2026via summary
Optimizing repository skills works, but only a little. A GEPA-optimized skill set added 4.9 points on three Kotlin repositories, measured by reverting merged PRs and replaying them as tasks. The authors say this is within run-to-run variance.
Judging a harness change needs real tasks and enough of them. The version scoreboard is the observational start; controlled replay waits for more history.
Kozyrev et al., Sep 2026read
Self-evolving agents carry specific risks: unreliable feedback, benchmark overfitting, changes that can't be undone, and rising complexity. Fully automated harness evolution (worker, evaluator, evolver) has been proposed, without numbers in its abstract.
Keep a human promotion gate and make every self-proposed rule land test-first (hard rule 2). Don't automate harness edits.
Zhou et al. survey, Sep 2026Seong et al., Apr 2026read

Evidence data

Keep the JSON tracked, and stop asking people to read it

The ledger and the per-PR review files are for machines. They stay in git because pr-loop's task worktrees are throwaway directories: anything untracked there disappears when the worktree goes, and history would split across machines. Git is the one store that survives, travels with every clone and CI run, and needs no service. People read the PR body, which is already the human view of one task, and a generated HTML report for the history, the same way graphify turns graph.json into graph.html.

One source, three audiences

  • Machines read JSON: CI validates it, retro aggregates it.
  • Agents read retro's text mode, capped at 60 lines, so a history of hundreds of tasks costs a few hundred tokens.
  • People read retro's HTML page: tasks, findings with their repros, ratchet candidates, and the version scoreboard.

Alternatives considered

  • Gitignored local files: lost with each task worktree and split per machine.
  • git notes: not pushed or fetched by default, and invisible in PRs.
  • PR comments only: every retro read would need gh and a network, and CI couldn't check the file in the diff.
  • A database or service: a new dependency for a few kilobytes of JSON.
Two closed loops

The ledger improves the project and Groundwork

pr-loop is the inner loop: one task, gate, probe, verifier. Retro adds two outer loops over many tasks. The first turns repeated findings into enforcement in the project. The second separates signals about the loop itself, tags them with the Groundwork version that produced them, and brings them back to this repository. This follows ponytail's one-shot report skills: groundwork-retro reads and reports, changes nothing, and never publishes a number it didn't measure.

Wave 1 · Fix, measure, close the cheating paths

TASK-1–6 · GW-018, GW-019
TASK-1

groundwork-init configures the PR status that pr-loop sets

bug · high
Why
pr-loop's last step runs backlog task edit <id> -s PR. A default Backlog.md config has no PR status, so every freshly initialized repo fails there. Found while initializing this repo's backlog.
Change
groundwork-init adds PR to backlog/config.yml statuses, keeping any existing ones. (This repo's config already has it, added by hand so the loop can run here.)
TASK-2

Ledger records handoff size and Groundwork version, and merges without conflicts

measure · high
Why
Token counts are null when the host hides them, so no later change can be shown to save anything (Liu 2026). The version tag is what lets Groundwork judge its own releases.
Change
handoff_bytes on every model route; groundwork_version from .groundwork-version on every line; the scaffold's .gitattributes sets merge=union on the ledger.
Decision
GW-018: evidence data is tracked JSON for machines; people read a generated view; handoff size is measured before anything is trimmed.
TASK-3

Analyzer flags weakened evals and baseline moves as high risk

guardrail · high
Why
Deleting a golden case currently reads as a healthy eval diff. Detecting edits to test files catches most reward hacking (EvilGenie).
Change
Reason eval-weakened at level high for a deleted or modified existing case, a changed test file, or any .eval-baseline.json edit; new cases stay unflagged; flagged files join review.targets.
Decision
GW-019: weakening the ground is high risk by default, and model output that decides state is checked by code.
TASK-4

pr_check.py validates the verifier's review JSON

guardrail · high
Why
"A finding without a repro never blocks" is the loop's central output rule and exists only as prose.
Change
--review checks enums, a new required question field, a repro on every blocking finding, and one verify record per standing id. It runs in CI and before REPAIR, and rejections are counted in the ledger.
TASK-5

Pre-commit blocks a baseline move without an ADR

guardrail · medium
Why
"The baseline moves only by a recorded decision" is prose today. A git hook enforces it for Claude Code and Codex alike.
Change
The scaffold pre-commit exits 1 when .eval-baseline.json is staged without a file under specs/decisions/.
TASK-6

Agents cannot bypass hooks with --no-verify or force-push

guardrail · medium
Why
A hook can't stop the flag that skips it. Decided: an emergency bypass is a human-only action.
Change
A PreToolUse hook blocks git commit with --no-verify/-n and git push with --force/-f. Claude Code's prefix-based deny rules would miss git commit -m x --no-verify, so this is a hook rather than a deny rule. Hard rule 5 is updated; Codex parity is recorded as a gap in GW-019.

Wave 2 · Pay for fewer tokens

TASK-7–9 · GW-020
TASK-7

Resident instruction file stays under 3,000 bytes

tokens · medium
Why
Loaded on every turn of every session. Overviews add 20%+ cost with no success gain; instructions are what agents follow (ETH, 2026).
Change
Keep role, toolchain one-liners, Gate, Commands and Hard rules; drop the Layout tree and loop narrative for links. groundwork-init's minimal file follows the same cap.
Depends
TASK-6, which edits hard rule 5.
Decision
GW-020: the resident context has a byte budget; everything else loads on demand.
TASK-8

Hooks print a bounded failure summary and the path to the full log

tokens · medium
Why
A failure pastes the whole log into context. Keep the pointer so the agent doesn't rerun to recover what was cut (Liu 2026).
Change
Failing test ids with their first assertion line, at most 40 lines, plus the log path. Success stays silent.
TASK-9

pr-loop loads per-state detail on demand

tokens · low
Why
16.9 KB loads whole on every run, though each template and schema is used in one state.
Change
SKILL.md keeps the state machine, roles, budget and routing (8 KB or less); detail moves to references/implement.md, verify.md and evidence.md. No rule changes.
Depends
TASK-2 and TASK-4, which edit the same sections.

Wave 3 · Repo loop

TASK-10–11 · GW-021
TASK-10

groundwork-retro: text for agents, HTML for people

repo loop · medium
Why
The ledger and review files hold the evidence of repetition the ratchet needs, and nobody reads them.
Change
A new one-shot skill with a stdlib ledger_report.py. Text mode (60 lines or fewer) prints rates, trends and recurring findings, plus one ready-to-run draft command when a group spans 3 or more tasks. --html writes one self-contained page with no network, gitignored.
Depends
TASK-2 (handoff size, version) and TASK-4 (question field).
Decision
GW-021: the project learns through drafted, human-promoted, test-first ratchets.
TASK-11

Ratchet drafts enter the loop, and people promote them

repo loop · low
Why
Small appended updates plus curation, never a rewrite (ACE); keep changes reversible (Zhou et al.).
Change
/pr-loop next runs retro first and files ratchets as drafts only. The debt rule accepts tasks <ids>. A ratchet's acceptance goes red on its recorded repros. No model edits instruction files from retro output.

Wave 4 · Groundwork loop

TASK-12–13 · GW-022
TASK-12

Retro separates Groundwork signals and scores Groundwork versions

groundwork loop · low
Why
Some signals are about the loop, not the project: a rejected verifier output, a task ending not met after call 2, a failed or substituted model route, repeated preflight bounces, a handoff over budget. With the version tag, a Groundwork change can be judged on real tasks.
Change
Fixed classification rules listed in the skill, and a per-version scoreboard: tasks, calls per task, repair rate, not-met rate, median handoff bytes.
Honesty
As in ponytail-gain: measured numbers only, null stays unknown, and no verdict for a version with fewer than 5 tasks.
Decision
GW-022: Groundwork improves from version-tagged loop signals that a person chooses to send upstream.
TASK-13

Retro writes a sanitized upstream feedback packet

groundwork loop · low
Why
Groundwork improves fastest from the repositories that use it, and sending project data out is a person's decision.
Change
--upstream writes counts, rule ids, GW ids, versions and the scoreboard; no code, paths, finding text or task titles. It prints the gh issue create command and never runs it. Here, a feedback issue becomes a draft labelled upstream.

Order

  • Ready now: TASK-1 to TASK-6 and TASK-8. backlog task list --ready shows them by priority.
  • TASK-1 first: without it, pr-loop can't finish in a new repo.
  • TASK-7 after TASK-6, and TASK-9 after TASK-2 and TASK-4.
  • TASK-10 once TASK-2 and TASK-4 land, then TASK-11 and TASK-12, then TASK-13.

Deferred, with the trigger to revisit

  • Hidden holdout evals (EvilGenie, CapCode): files in the repo are readable by the implementer. Revisit if TASK-3 flags tampering in real runs.
  • Controlled PR-replay ablation (Skill Issue): once the ledger holds 20 or more tasks per version and the scoreboard shows a difference worth confirming.
  • Mining prompts/raw/ for corrections: noisy and privacy-sensitive. Revisit after retro proves useful.
  • Cache-stable handoff ordering (TokenPilot): subagents start fresh, so the payoff is small.
Not doing

Ideas the evidence argues against

IdeaWhy not
A second reviewer agent or more review roundsExtra reviewers cut success by 8%; more than four handoffs almost always fail. GW-017 stays at two calls.
Letting a model rewrite CLAUDE.md or skills from the ledgerLLM-written context files lowered success by about 3%, and whole rewrites cause context collapse (ACE). Ratchets are drafts a person promotes.
Sending feedback upstream automaticallyProject data leaving the repository is a person's call. Retro prepares the packet and prints the command.
A Groundwork-owned compaction layerThe host already compacts, and the analyzer's rule-based trimming is the efficient first stage. Another summarizer adds cost and hidden re-fetches.
Fully automated harness evolutionNo reported numbers, plus the known risks of unreliable feedback and irreversible changes.
More resident rules to cover new casesEach resident byte is paid on every turn. New rules go into hooks, tests or files loaded on demand.

Decisions, 2026-09-29

What the maintainer decided

  1. Agents may not bypass hooks. Emergency --no-verify becomes a human-only action. Built as a PreToolUse hook, because prefix deny rules miss reordered arguments (TASK-6).
  2. Ratchet threshold is 3 tasks. Adjust later from retro's own output (TASK-10).
  3. Backlog.md is initialized in this repository. Agent-instruction files were skipped to protect the resident budget, and the PR status was added by hand. Doing this exposed the TASK-1 bug. TASK-1 to TASK-13 are filed.
  4. One ADR per theme: GW-018 evidence data and measurement, GW-019 guardrails, GW-020 context budget, GW-021 repo loop, GW-022 Groundwork loop.
  5. Evidence JSON stays tracked; people read the PR body and retro's generated HTML, never the raw files (TASK-2, TASK-10).
